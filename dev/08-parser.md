# Parser rewrite (2026-10-12)

The CommonMark-only block parser (`src/syntax/`, commonmark.js's block phase ported,
the whole document re-parsed on every edit) is replaced by `src/parsing/`: an incremental,
lossless, flavored parser with inlines and an HTML renderer. The outline, `OutlineDoc` and the
commands run on it. `Config.format` is renamed to `Config.flavor`.

Numbers: 489 tests passed and 9 were pending when `07-bugs.md` was written; now 576 pass, 0 fail
and 8 are pending. The behavior spec's 460 examples each run in all three flavors.
`src/parsing/` is 4,991 lines (of which `entities-data.ts` is 6 lines of generated data) and
`test/parsing/` is 883. Deleted: `src/syntax/` (938 lines), `src/block.ts`, `test/syntax.test.ts`,
`test/commonmark.test.ts`. Nothing is committed: `.git` was read-only for this session.

### Line-relative offsets

Every offset in the tree is relative to its line: a block holds line numbers, and its attributes
(an item's marker, a task's checkbox, a table cell) hold offsets within their line.

```ts
export interface TaskMarker {
  readonly checked: boolean;
  readonly status: string;   // the character in the brackets (a space when unchecked)
  readonly start: number;    // the checkbox, brackets included, from its line's start
  readonly end: number;
}
```

This is the design decision that makes everything else cheap. An edit never shifts anything below
it, so unchanged records and blocks are reused as they are, and a whole subtree can be kept by
identity. `syntax.offset(line, rel)` converts when an absolute position is needed, and `LineInfo`
(prefix pieces, leaf, content start) is absolute and built per line on demand.

It cost one round of churn in the consumers: `commands.ts` used `block.markerFrom!` everywhere and
now calls `doc.markerFrom(block)`. Worth it, and the compiler found every site.

## 3. The line machine

commonmark.js's block algorithm, generalized so the block types come from the flavor:

- **Frames.** The open blocks are a stack of immutable frames.
- **`BlockSpec`.** What an open block does with a line:

  ```ts
  export interface BlockSpec<F extends Frame = any> {
    readonly type: string;
    readonly container: boolean;        // holds other blocks
    readonly acceptsLines: boolean;     // takes text lines
    readonly interruptible?: boolean;   // block starts are still tried on its lines
    continue(m: Machine, frame: F, index: number): 0 | 1 | 2;  // 2 = line fully handled
    canContain?(child: BlockSpec): boolean;
    childAdded?(frame: F): F;
    addLine?(m: Machine, frame: F, index: number): void;
    close?(m: Machine, frame: F): void;
  }
  ```

- **`BlockStart`.** Tried in the spec's order of precedence; returns 0 (no match), 1 (a container
  opened, keep looking) or 2 (a leaf, stop). An extension places its own `before` or `after` a
  named start.

The state after every line is kept. Frames are immutable, so a state costs only the frames that
changed. Each line's record is:

```ts
export interface LineRecord {
  readonly depth: number;            // containers open after the line
  readonly opened: readonly Opened[];
  readonly pieces: readonly Piece[]; // what each container consumed: `>`, a marker, indentation
  readonly leaf: LeafRole | null;
  readonly lazy: boolean;            // a paragraph continued through containers that didn't match
  readonly ahead: number;            // how many lines after this one the machine read
  readonly text: number;             // where the line's text starts in its leaf, from the line's start
  readonly pad: number;              // spaces the leaf's text starts with that the line doesn't have
}
```

`pad` is the one field that isn't obvious: when a container consumes part of a tab, the leaf's text
starts with the rest of that tab, which is in no line's text. Recording it lets code lines and
inline text be read straight off the records without re-deriving tab columns.

**Containing the spec's two backward effects.** Markdown is not a left-to-right grammar in two
places: a setext underline or a table's delimiter row changes what the paragraph above it was, and
frontmatter's closing fence decides its opening. The machine confines both. A rewrite can reach
only the open paragraph's lines (`rewriteRole`); a lookahead is recorded on the line (`ahead`), so
an edit within its reach restarts there. Without this, incrementality would be unsound in exactly
the places nobody tests.

## 4. Incremental update

`update(changes)`:

1. **Restart** at the first changed line — or earlier: at a line whose lookahead reaches the
   change, or at the start of a paragraph still open there.
2. **Re-read** lines until the state equals the old parse's state at the corresponding old line.
3. **Reuse** the old records and states for everything after that.

Convergence is usually immediate: a keystroke inside a paragraph re-reads 2 lines of 10,000.

**Tree sharing.** When the re-read records equal the old ones and no line was added or removed, the
whole block tree object is reused:

```ts
let tree: Tree | null = null;
if (this.tree && lineDelta === 0 && n === oldN) {
  const from = open.spec === PARAGRAPH ? restart - (open as ParagraphFrame).lines : restart;
  let same = true;
  for (let l = from; l <= reread.to && same; l++) same = sameRecord(records[l]!, this.records[l]!);
  if (same) tree = this.tree;
}
```

`OutlineDoc` then keeps its outline, nodes and ids by identity. That is the common keystroke: the
text changed, the structure didn't, so nothing downstream recomputes.

**What is still not incremental:** when a line is added or removed, the tree and line table are
rebuilt from the records. That is O(lines) and cheap (about 2 ms at 10k lines), but it is the
largest remaining win (§10).

## 5. Inlines

commonmark.js's inline algorithm — delimiter stack, bracket stack, the spec's resolution rules —
over a leaf's *inline text*: its content lines without container prefixes, with a map back to the
source. Nodes hold offsets into that text, so every inline maps to its source character for
character. That is tested as an invariant, not assumed.

Four kinds of rule, which is all four flavors have needed:

```ts
interface InlineRule    { triggers: string; parse(p): boolean }           // code, autolinks, math
interface DelimiterRule { char: string; strict?: boolean;                 // emphasis, ~~, ==
                          accepts?(length): boolean;
                          match(opener, closer): { use: number; type: string } | null }
interface BracketRule   { phase: 'before' | 'after'; resolve(p, opener): boolean }  // links, footnotes
interface TextRule      { process(p, node): void }                        // GFM's extended autolinks
```

**Cache.** Inlines are cached per leaf text, keyed on the document's reference and footnote
definitions, so a keystroke re-parses one leaf's inlines and nothing else.

**Linear time.** Adversarial inputs are linear and held to a time budget by
`pathological.test.ts`. The fixes, each found by that suite:

| input | problem | fix |
| --- | --- | --- |
| `[a](b` × n | quadratic re-scanning of destinations | parenthesis nesting capped at 32, as cmark does |
| `[[[[…` | quadratic bracket deactivation | barrier ids instead of walking the stack |
| `<!--` × n | re-scanning for a closer that isn't there | per-position closer flags (ported from cmark) |
| `$x` / `[[` runs (Obsidian) | re-scanning | memo of failed closers |
| deeply nested lists | `findNextNonspace` rescanned whitespace | per-line cache of the scan |
| one long paragraph, edited | state comparison was O(paragraph) per line | content equality memoized per paragraph |
| very deep nesting | stack overflow | the renderer, freezing and all walks made iterative |

## 6. Flavors

```ts
export const gfm = defineFlavor('gfm', [gfmCore, table, tasklist, strikethrough, autolink, tagfilter, footnotes]);
export const obsidian = defineFlavor('obsidian', [...obsidianExtensions]);
```

An `Extension` contributes block starts (placed, with the characters they can begin with), block
specs, leaf builders (a table's rows and cells), inline text for its leaves, the four kinds of
inline rule, and render rules. It can also `remove` rules by name, which is how Obsidian turns off
single-tilde strikethrough. `defineFlavor` compiles the list once into start lists, trigger tables
and renderer maps; CommonMark is the first extension of every flavor.

Obsidian is GFM as Obsidian reads it (tables need a pipe, tasks take any status character,
strikethrough is `~~` only) plus its own syntax. Obsidian has no spec, so what `obsidian.ts` reads
is pinned by 32 example tests, drawn from its help pages and from what true-outliner measured
against Obsidian 1.13.

**Room for Pandoc and Quarto.** Every piece has a hook that fits:

| Pandoc/Quarto syntax | hook |
| --- | --- |
| YAML metadata | `frontmatter`, already written |
| fenced divs `::: {.note}` | a container `BlockSpec`, like callouts |
| attributes `{#id .class}` | a `TextRule`, or an after-phase bracket rule |
| citations `[@key]` | a bracket `kind` |
| definition lists | a block spec that continues a paragraph |
| Pandoc's list markers `#.`, `(a)` | replace CommonMark's item start by name |
| inline notes `^[...]` | already written for Obsidian |

Nothing in the machine or the inline parser is CommonMark-specific beyond the rules it is handed.
That claim is only half-proven: Obsidian exercises containers, leaves, delimiters, brackets and
lookahead, but no flavor has yet *replaced* a CommonMark rule, which is what Pandoc's list markers
would do first.

## 7. Rendering

`renderHtml` writes HTML exactly as commonmark.js does, which is what makes spec examples
checkable at all. Where cmark-gfm differs, a GFM render rule says so: no `<strong>` directly inside
another, cmark's line endings between blocks (commonmark.js compares the last write, cmark the
last character), and the tag filter. Extensions render their own node types; footnotes number
themselves in a start hook and write their section in an end hook. `escapeRawHtml` writes raw HTML
as text, for untrusted input such as the demo's preview.

## 9. Reference parsers: bugs and discrepancies

This is the most useful thing the differential produced. All examples below were verified today
against cmark-gfm (built from source, `--unsafe`), commonmark.js master, markdown-it 15, marked 18
and micromark 4.

### 9.1 cmark starts an HTML block on a lazy continuation line

```
- a
<x>
```

| parser | output |
| --- | --- |
| ourus, commonmark.js, markdown-it, micromark | `<ul>\n<li>a\n<x></li>\n</ul>` |
| cmark-gfm | `<ul>\n<li>a</li>\n</ul>\n<x>` |

HTML blocks of type 7 (a bare open tag) cannot interrupt a paragraph, so `<x>` is a lazy
continuation line of the item's paragraph. cmark starts an HTML block anyway. Same with `> a` /
`<x>`. ourus follows the spec and the majority.

### 9.2 cmark calls a list tight when a thematic break hides a blank line

```
- a
  ***

- b
```

| parser | list |
| --- | --- |
| ourus, commonmark.js, markdown-it, micromark, marked | loose (`<p>a</p>`) |
| cmark-gfm | tight (`a`) |

The two items are separated by a blank line, so the list is loose. cmark's
`S_set_last_line_blank` doesn't record the blank line when the item's last child is a thematic
break, so it reports the list as tight. Also with `1.` / `***`.

### 9.3 cmark keeps the spaces left where a reference definition was taken out

```
10. [a]: /u
  b
```

| parser | output |
| --- | --- |
| ourus, commonmark.js, micromark | `<ol start="10">\n<li>b</li>\n</ol>` |
| cmark-gfm, marked | `<li>  b</li>` (two leading spaces) |
| markdown-it | `<li></li>\n<p>b</p>` (different again) |

The item's paragraph begins with a reference definition, which is consumed; `  b` is a lazy
continuation line, and its indentation is not content. This is the only class of difference left
in the cmark-gfm differential: all 4 remaining mismatches out of 19,708 are this, reached through
footnote definitions and nested containers.

### 9.4 `[a]: /u` followed by `---`: both references are wrong, differently

```
[a]: /u
---
```

| parser | output |
| --- | --- |
| **ourus, markdown-it, marked, micromark** | `<hr />` |
| commonmark.js | `<p></p>\n<hr />` — a stray empty paragraph |
| cmark-gfm | `<p>---</p>` — neither a break nor a heading |

The definition consumes the first line, leaving no paragraph for `---` to underline, so `---` is a
thematic break. commonmark.js leaves behind the emptied paragraph node; cmark treats the `---` as
paragraph text, which is right for `===` (spec example 216) but wrong for `---`, which is a
thematic break in its own right. ourus is with the majority. **This is the one case where ourus
disagrees with both of its oracles and is, as far as I can tell, correct.**

### 9.5 commonmark.js 0.31.2 bugs fixed on master, which ourus follows

Found by running commonmark.js's own regression file. Both were fixed upstream after the 0.31.2
release, and cmark already did the right thing:

- **The item rule checked blankness before indentation.** Master checks indentation first. This
  changes `- \n\t\n  a`, among others.
- **Info strings were trimmed before unescaping,** not after.

The structure oracle in `test/oracle.ts` patches the reader's item rule to master's behavior, or
it would report false mismatches.

### 9.6 Deliberate deviation from cmark-gfm: where a task checkbox is recognized

GFM's spec says a task list item is a list item whose first block is a paragraph beginning with a
checkbox. cmark-gfm additionally requires the checkbox to be at the start of a *line*, so it misses
both of these:

```
> - [ ] q        cmark: <li>[ ] q</li>        ourus: <li><input type="checkbox" disabled=""> q</li>
- - [ ] n        cmark: <li>[ ] n</li>        ourus: <li><input type="checkbox" disabled=""> n</li>
```

ourus follows the spec's text, because an outliner must recognize tasks inside quotes and nested
lists. `tasklistExtension({ cmark: true })` restores cmark's behavior for the differential.
(Uppercase `[X]` is *not* a deviation — cmark-gfm accepts it too. An earlier note of mine said
otherwise; it was wrong.)

### 9.7 micromark is extraordinarily slow on nested lists

Not a correctness bug, but worth recording: on the 10k-line outline document (nested bullets),
micromark takes **1.5 seconds** where every other JS parser takes 10–30 ms. On prose of the same
size it takes 62 ms — still the slowest, but by a normal margin. Something in its list handling is
superlinear in nesting depth or document size. I did not chase it further.

### 9.8 Smaller things found along the way

- **cmark's `cmark_isspace` excludes `\v`,** unlike the usual whitespace set. This matters for
  table cell trimming and autolink boundaries.
- **cmark-gfm never opens an image at `![^`,** so `text![^1]` keeps the `!` as text. That is a
  footnotes-extension behavior, not a core one.
- **cmark-gfm tries extension block starts last,** after all core starts, and keeps a per-paragraph
  "table visited" flag so a failed table start isn't retried. ourus mirrors both.
- **cmark measures some offsets in bytes rather than characters.** I noted this early but could
  not construct a reproducing case today, so I am recording it as unverified rather than as a
  known divergence.

Reading it:

- **Per keystroke, ourus is ~120× faster than the old parser** (15.5 → 0.13 ms) and on par with
  Lezer, the other incremental parser in the list.
- **A new line costs 2.2 ms**, against Lezer's 0.09, because the tree is rebuilt whenever the line
  count changes. This is the one number that is clearly beatable.
- **Full parse beats the old parser** (10.4 vs 15.6 ms) while recording strictly more.
- **true-outliner's block pass is ~1.5× faster**, but it is block-only by design: no lazy
  continuation, no indented code, quotes as runs of `>` lines, no inlines.
- **Full HTML is 1.5–2× slower than commonmark.js**; inlines dominate and have not been tuned.
- **cmark (C) is 5–7× faster** than ourus for HTML, which is the expected native gap.

Through the editor core, a keystroke's `OutlineDoc.apply` went from 23.7 ms to **0.11 ms**.
Commands still take 14–37 ms at 10k lines, and that is now *entirely* the command layer: writing
and verifying the whole document.

Caveats: p95s are noisy (up to ~60 ms where medians are 10–15 ms), and on the one-root-bullet
document a keystroke update measures 0.93 ms rather than 0.12. Neither is chased down.

## 11. Integration

- **`OutlineDoc`** holds a `Syntax`; `apply` calls `syntax.update`, and keeps the outline, nodes
  and ids when the tree is shared.
- **Config:** `flavor: 'commonmark' | 'gfm' | 'obsidian'`, default `commonmark`.
- **Outline:** tables, math and comment blocks, and footnote definitions are atoms; a callout's
  title line is its quote's text; frontmatter is a preamble with no node.
- **Demo** (`demo/cm6/`): a Flavor select (Obsidian by default) and a renderer select — ourus,
  commonmark.js, markdown-it, marked, micromark, remark, showdown — each configured for the chosen
  flavor, with highlight.js and KaTeX applied after any of them. `npm run demo:smoke` checks all
  21 combinations. The bundle is a classic script, not a module, so the page works from `file://`.

### Bugs this found in the command layer

Making Obsidian the demo's default immediately exposed command bugs, because `commands.ts` had
only ever run under CommonMark:

- **Tasks.** In GFM and Obsidian, `- [ ] ` with nothing after the checkbox has *no paragraph* —
  the checkbox is the whole item (cmark-gfm agrees). The commands assumed a paragraph, so Enter on
  a task was refused and Backspace after an empty checkbox misbehaved. `doc.headLines` now returns
  the checkbox as the item's text in that case.
- **Callouts.** Enter in a callout title dropped the `> ` prefix. There is now
  `splitCalloutTitle`: the rest of the title starts the body. A line break inside a title, or
  Enter inside `[!type]`, is refused.

Both are now covered: every spec example runs in all three flavors unless it names one, and the
command property tests draw the flavor at random. Verification rejects about 1.3% of commands on
random messy documents in each flavor — so no flavor is systematically worse encoded.

Things to know before changing the parser:

- The three test suites that will catch a mistake fastest: `test/parsing/spec.test.ts` (exactness),
  `test/parsing/incremental.test.ts` (incremental = full) and `test/parsing/invariants.test.ts`

  incrementality change.

  compared there, or the parser will converge too early and produce a stale tree — silently.
- Any new backward-looking rule must either mark `ahead` or confine itself to the open paragraph.
- `sameRecord` in `syntax.ts` decides tree sharing. A new record field must be compared there too.
- The 8 pending spec examples are all in `zzz-redesign.md` and are undecided behavior, not
  failures.

## 13. Where this should go

In rough order of value.

**1. Incremental tree and line table.** The only clearly-beatable number in §10. On a line-count
change, shift line numbers past the edit and rebuild only the spine of blocks the edit touched,
instead of rebuilding from all records. Because offsets are line-relative, untouched subtrees need
nothing but a line-number shift. Expected: 2.2 ms → under 0.2 ms, matching Lezer. This is also the
prerequisite for the next item.

**2. Make commands verify incrementally.** Commands are now 99% of the cost of an edit (14–37 ms
against the parser's 0.1). They re-encode and re-verify the whole document. With the tree
incremental, verification could compare only the outline around the change. This is the single
biggest user-visible win left in ourus, and it is a *command-layer* project that the parser work
has now unblocked.

**3. Flavor-aware escaping in commands.** A split or join that puts `$$`, `%%`, `|` or `:::` at the
start of a line can change what Obsidian reads. Today verification catches it and refuses the
command — correct but unhelpful. `startsBlock` should become a flavor method, so the commands
escape instead of refusing. This is why Mod-Backspace in an Obsidian callout is refused today.

**4. Pandoc and Quarto flavors.** Mostly an exercise in the hooks of §6. The honest test of the
extension design is whether a flavor can *replace* a CommonMark rule (Pandoc's list markers), not
just add to it. I'd start there rather than with the easy additions, because that's where the
design will break if it's going to.

**5. Drop Lezer from the demo.** CodeMirror highlights Markdown with its own Lezer parse, so the
demo parses every document twice. A CM6 `Language` backed by ourus's `Syntax` would halve that and
make highlighting agree with the outline — tasks inside quotes, callouts, wikilinks all highlight
correctly only if the highlighter shares the parser's flavor. §10 shows ourus and Lezer are
comparable in speed, so this costs nothing.

Bets worth trying, with real upside and real risk:

**6. Treat the record array as the only state, and the tree as pure derivation.** Today `Syntax`
holds records, states, a lazily built tree, a line table and an inline cache, with sharing logic in
`update` for each. If the tree were a pure, memoized function of a record range, tree sharing would
fall out of memoization rather than being hand-written (`sameRecord` and the `lineDelta === 0`
special case would both disappear). This would simplify the trickiest part of `syntax.ts` and is
the change most likely to make the whole thing smaller. Risk: a persistent-structure rebuild is
easy to get subtly wrong, and the current code is tested to death.

**7. Give extensions a declarative shape for simple block starts.** `obsidian.ts` is 541 lines, and
much of it is near-identical container/leaf boilerplate — math blocks and comment blocks are the
same shape with different fences. A tiny combinator (`fencedBlock` already exists; generalize it)
could cut that substantially, and would make Pandoc's fenced divs a one-liner. Risk: combinators
that don't quite fit are worse than explicit code; only do it after Pandoc proves the shape.

**8. Reconsider whether `LineInfo` should exist.** It is absolute-offset, built per line on demand,
and exists mostly because the outline and commands predate line-relative offsets. If consumers
moved to records plus `offset(line, rel)`, a whole materialization layer and its cache would go.
Worth measuring before attempting: it may be load-bearing for command readability.

**9. Property-test the flavors against each other.** Today each flavor is tested against its own
oracle. A cheaper and sharper property: for any document with no flavor-specific syntax, all three
flavors must produce identical trees. That would catch extensions that accidentally change
CommonMark behavior — the failure mode most likely to appear as Pandoc and Quarto land.
